<p>「上周三是不是有人用这个号跑过脚本？」当这个问题出现时，多数团队才发现自己只有一张 IP 采购单，没有任何可查的记录。操作留痕不是买完代理再补的功能，它由四层信息叠起来：网络层的连接日志、应用层的会话记录、管理层的分组与成员权限、审计层的留存与检索。这篇按层往下拆，每层给出具体要开什么、字段长什么样、缺了会怎样。</p>

<h2>一、留痕分四层，缺一层就查不到人</h2>
<p>四层各自回答不同的问题，任何一层缺失都会让链条断掉。网络层回答「从哪来、什么时候来」，应用层回答「做了什么」，管理层回答「归谁」，审计层回答「还能不能翻出来」。只买代理不做分组，等于有地址没有归属；只做分组不开日志，等于有名单没有时间线。</p>

<h3>四层各自的承载物</h3>
<p>网络层落在代理网关或自建 Squid、3proxy 的 access.log 里；应用层落在浏览器历史、客户端缓存或自动化脚本的运行记录里；管理层落在代理后台的分组、成员、白名单配置里；审计层落在你自己的日志系统和保存策略里。前三层供应商可能提供一部分，第四层基本只能自己做。</p>

<h3>断链最常见的三种情形</h3>
<p>一是多人共用一个子账号，日志里全是同一个用户名，追不到人；二是分组名随手起，三个月后没人知道「group2」是谁；三是日志只留七天，等发现问题时已经被轮转掉了。三种情形都不需要额外花钱，只需要在配置时多想一步。</p>

<h2>二、网络层：三列日志就能回答大半问题</h2>
<p>不需要上复杂的可观测平台。代理网关的访问日志里，时间戳、认证用户名、出口 IP 这三列，已经能回答「谁在什么时候用了哪条线」。再补上目标域名和发送/接收字节数，就能判断是普通对话还是大批量任务。</p>
<img src="/tp.png" alt="代理网关访问日志界面展示时间戳、用户名、出口地址与流量列">
<p>自建场景下，Squid 的 access.log 默认格式里就有时间、耗时、客户端 IP、状态码、字节数和 URL；3proxy 的日志行更短，需要靠 %u 之类的占位符把用户名带出来。配置时先确认用户名字段真的写进去了，很多默认模板是不带的。</p>

<h3>子账号必须一人一个</h3>
<p>这是留痕的地基。五个人共用一个代理账号，日志里五条记录长得一模一样，事后无法区分。给每个成员单独开子账号或独立凭据，成本几乎为零，价值在出问题那天体现。成员离职时也能一次性停用，不影响别人。</p>

<h3>把日志推到自己的存储里</h3>
<p>供应商后台的日志通常只保留 7 到 30 天，且导出有行数限制。用 rsync 或简单的定时任务每天拉一次，落到自己的对象存储或时序库里，保留 90 到 180 天。文本日志按月压缩后体积极小，一天十万行的量级也就几十兆。</p>

<h2>三、分组是索引，权限是闸门</h2>
<p>分组决定「查的时候按什么维度筛」，权限决定「谁能看到这一层」。两者要一起设计，否则会出现「能查但查不全」或者「谁都能查」两种尴尬。</p>

<h3>分组按什么维度切</h3>
<p>常见三种切法：按业务线（内容、投放、客服）、按地区（美东、西欧、东南亚）、按账号批次（老号、新号）。一个团队只选一种主维度，另一种作为标签附加。主维度频繁变动会让历史数据失去可比性，所以选完至少稳定半年。</p>

<h3>权限的最小集</h3>
<p>普通成员只看自己的使用量；组长能看本组全部；管理员才能改配置、删日志。删除权限单独收口，任何情况下不允许使用者自己删记录。多数代理后台支持角色模板，配一次就能复用，别用「都给管理员」图省事。</p>

<h2>四、把「谁、何时、从哪、做了什么」拼成一条</h2>
<p>四要素凑齐才算一条能用的记录。网络层给「何时、从哪」，应用层给「做了什么」，管理层给「谁」。拼接的钥匙是子账号名加时间窗，不需要把两侧数据做严格的主键关联，按分钟对齐已经够用。</p>

<h3>一个可执行的查询流程</h3>
<p>先拿到疑似时间点，去网关日志筛出该时间窗内所有子账号与出口；再用子账号名去应用层日志或浏览器历史里找对应会话；最后回管理后台确认这条出口当时的归属分组。三步走完通常十分钟内能定位，前提是子账号一人一个。</p>

<h3>时间要对齐时区</h3>
<p>网关日志常用 UTC，浏览器历史和业务系统常用本地时间，差八小时会让整条线索错位。统一在采集端转成同一时区并在日志头写明，比事后心算可靠。跨地区团队尤其要固定一个基准时区。</p>

<h2>五、留存多久、谁能删，要写在制度里</h2>
<p>留存周期不是越长越好，要跟业务风险和存储成本平衡。登录类记录留 90 天能覆盖大多数排查需求；涉及支付或对外承诺的操作，留 180 天更稳。超过半年的冷数据转对象存储，成本可以压到热存储的几分之一。</p>

<h3>删除要走审批</h3>
<p>任何删除动作留一条元记录：谁在什么时候删了哪段区间的数据、理由是什么。这条元记录本身不可删。做法很土但有效，多数事后争议都卡在「到底有没有人动过」这一点上。</p>

<h3>交接时同步移交</h3>
<p>成员离职、分组调整、供应商更换，三种情况下留痕链条最容易断。交接清单里明确写上「日志采集任务已迁移」「分组命名规则已同步」「历史数据保留在哪个桶」，比口头交代靠谱得多。</p>

<h2>常见问答</h2>
<h3>供应商后台能查到每个成员的操作记录吗？</h3>
<p>答：多数只能查到连接级记录，也就是子账号、时间、出口和流量，看不到你在页面上点了什么。应用层的操作需要自己在浏览器或脚本侧留痕。买之前问清日志字段和保留天数，别默认「后台都有」。</p>

<h3>只有一条出口、多人共用，还能追溯吗？</h3>
<p>答：能追到时间窗，但难以精确到人。补救办法是给每人开独立子账号，即使共用同一出口 IP，日志里的用户名也能区分。如果供应商不支持子账号，就在本地网关做一次认证转发，把用户名透传下去。</p>

<h3>日志留 90 天够不够？</h3>
<p>答：看业务性质。纯内部使用、无对外承诺，90 天通常够；涉及订阅支付、客户交付或合同履约，建议 180 天并按月归档。留存成本主要是存储，文本日志压缩后开销很小。</p>

<h3>用浏览器无痕模式是不是就没有留痕了？</h3>
<p>答：无痕只清本地记录，代理网关侧的连接日志照常生成。反过来说，如果只依赖浏览器历史做追溯，无痕模式会让应用层这段空白。所以关键记录要落在网关和自建日志里，而不是依赖客户端。</p>

<h2>合规提示</h2>
<p>留痕的目的是内部管理与故障排查，采集范围应限于网络连接与必要的操作记录，不应记录与业务无关的个人隐私内容。采集前向团队成员明示范围与用途，符合个人信息保护相关法律要求。</p>
<p>日志的访问权限按最小必要授予，导出与共享需经审批。涉及跨境传输的日志数据，应确认符合数据出境的合规要求。</p>
